> **评审后更正**：本页数值和二进制哈希保留的是评审前基线。该会话存在 32 Hz 的 Microsoft Remote Display Adapter，不能作为物理显示器性能验收；此前“触发 DXGI 采集决策”的结论已撤回。最新实现与验证见 [评审修正记录](../reviews/P0-corrections-2026-11-06.md)。

## 结论

工程和四个技术原型已实现；双架构构建、35 个单元测试、静态分析、导入检查，以及当前桌面的像素/资源检查通过。**P0 尚未全部验收通过：30 fps 无丢帧目标未达到，指定双 4K 环境和旧系统尚未验证。** 尚未开始 P1 托盘、INI 和全局热键功能。

评审后的结论是：这里只测到了当前测试会话中的同步与处理成本。约 31.25 ms 的固定周期与远程显示适配器的 32 Hz 一致，存在环境影响的可能；尚不能判定真实物理显示器上的 BitBlt 或 GPU 回读是瓶颈。应在合格本地物理显示器上重测，再按 AC0-7 决定是否需要 DXGI。

采集计时包含 **BitBlt + GdiFlush + 复制到复用 BGRA 缓冲**，不应称为纯 BitBlt API 时间。浮层使用预计算遮罩、双缓冲和变化区域绘制；计时覆盖 WM_PAINT 与 GDI flush，**不包含 DWM 呈现延迟**，不能代替热键到显示或输入延迟指标。

贴图校验覆盖 100% / 80% 整体不透明度、逐像素 Alpha 和位置；不透明像素要求完全一致，混合边缘允许合成舍入的 1 级通道误差。这里没有实现 P4 的缩放、收缩、回收站等交互。

GDI/USER 零增量只说明这些受测循环的对象数量回到基线，不代表私有内存、所有内核句柄或 8 小时稳定性已经验收。

最终复测：[x64 GIF](data/x64-Release-gif-final.json)、[x86 GIF](data/x86-Release-gif-final.json)。两次都是 1280×720、目标 30 fps、10 秒；采集实际桌面上的已知动画，捕获后逐像素与源图样比较，编码后再用 WIC 解码并与捕获帧的 RGB 哈希核对。

| 计划帧数 / 实际捕获并解码帧数 | 300 / 124 | 300 / 122 |
| 丢失节拍 | 176（58.67%） | 178（59.33%） |
| 解码帧差异 | 0 | 0 |

| 完整实验单帧工作平均耗时 | 63.36 ms | 65.03 ms |

上述丢帧率属于**顺序运行的测试实验**：它还串行绘制测试图样、等待 DWM、核对像素和写文件，不能直接当作将来生产录制器的丢帧率。即便扣除显式测试工作，BitBlt 内部仍可能受到远程显示同步的影响，不能据这些数字作物理显示器采集选型。该顺序实验已改为仅验证正确性，吞吐使用独立图样进程和有界采集/编码流水线另测。

实现包含精确调色板、Wu 方差量化、LZW、GIF89a 全帧流式写出和累计延时补偿；没有采用第三方运行库。GIF 格式依据 [原始 GIF89a 规范](https://giflib.sourceforge.net/gifstandard/GIF89a.html)。测试动画不超过 8 色，精确路径有实测数据；Wu 只完成单元层面的确定性、调色板和误差校验，复杂视频的质量/吞吐尚未验收。

目前只保留一个待写压缩帧；没有生产版差分矩形、透明优化、采集/编码线程池、鼠标、锁屏暂停、预览或 60 秒内存峰值验证。这些属于 P5。

### x86 中途不匹配的调查

初次完整运行在 tick 157 出现像素不匹配，立即终止并删除部分 GIF，见 [原始记录](data/x86-Release.json)。增加诊断后，另一次在 tick 0 发现 53,446 个差异像素，首个差异点命中了其他窗口，见 [诊断记录](data/x86-Release-gif-diagnostic.json)。当时的诊断尚不能单独确认具体原因。

随后增加“每帧绘制前重新置顶测试图样窗口，保持不激活”的可见性设置，并保留严格校验；**没有重试失败帧或降低门槛**。最终两个架构均完成整段录制，全部捕获图样和解码校验通过。这个结果支持窗口可见性是测试干扰因素，但不把原始失败记录删除，也不据此断言所有外部遮挡都已解决。

## 推荐后续实施顺序

1. **P0 补验收**：在真实双 4K、175% 和混合 DPI/负坐标布局重跑；补纯净系统、Win7 及 GIF 播放检查。当前会话无法替代这些配置。
2. **P1 常驻框架**：复用 Win32/RAII/兼容层，实现托盘、热键、INI 热重载、单实例。位图按需创建并释放，独立验收空闲内存和 CPU。
3. **P2/P3**：保留 GDI 双缓冲和变化区域方案；后续增加标注时仍需重新评估双 4K 绘制成本，不能以本次矩形原型代表全部编辑器性能。
4. **P5 风险处理**：先在合格本地物理显示器上验证独立采集/编码流水线，再决定是否开发 DXGI；保留 Win7 BitBlt。当前两种 BitBlt 模式耗时接近，可能被固定同步成本主导，不能推断它们在物理设备上等价，也不能据此断言关闭 CAPTUREBLT 没有收益。

工程没有为追求一次通过而改动设计中的阈值。按设计文档 §3.3 和 AC0-8，下一阶段前应评审本报告中的采集路径结论与未验证项。
