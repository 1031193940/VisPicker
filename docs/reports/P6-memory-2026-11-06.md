# VisPick P6 私有提交排查与复测

## 排查结果

- 0.5.1 的 420.969 秒报告在第 16 轮达到 8,863,744 B，较第 3 轮的 8,302,592 B 高 6.76%。贴图关闭后为 8,404,992 B，随后 448 KiB 增量来自录制关闭与 GIF 校验这一合并阶段。最后一轮为 8,392,704 B。见 [0.5.1 原始报告](data/review-0.5.1/soak-420s.json)。
- 原生产代码加分段采样后，在 309.681 秒遇到首像素不匹配，报告保留了此前 13 轮。新增阶段读数显示 GIF 解码和合成结束后可增加约 232 KiB 私有提交。附近的会话、电源和锁定事件没有提供足够证据解释这次采集差异。见 [原生产代码对照](data/p6-0.5.2/baseline-soak-interrupted.json) 和 [调用记录](data/p6-0.5.2/baseline-soak-invocation.json)。
- 同进程 WIC 对照保留第 3 轮基线 8,462,336 B。第 9 轮从录制关闭后的 8,347,648 B 增到解码后 9,191,424 B，两秒空闲采样 9,166,848 B（+8.33%），下一轮回落至 8,376,320 B。第 12 轮再现，空闲峰值 9,256,960 B（+9.39%）。两次变化集中于同一约 2 MiB `MEM_PRIVATE` 保留区，解码前后默认堆在用字节持平。快照表明该区域的已提交页短时增加，随后减少。快照无法确定该区域内部的具体分配调用或活跃块状态。见 [420 秒报告](data/p6-0.5.2/in-process-soak-420s.json)、[阶段差分](data/p6-0.5.2/in-process-memory.jsonl) 和 [会话观察](data/p6-0.5.2/in-process-session.log)。
- 独立 WIC 解码也能产生私有提交波动。两张录制样本交替解码 100 次，默认堆在用量只在 1,840 B 范围内变化，提交和空闲区间显著更大。对两种图样分别做三组复用帧缓冲的对照，像素与时间戳校验和一致，峰值改善没有跨次复现。见 [独立对照](data/p6-0.5.2/wic-allocation-ab.txt)。

## 修改

- `Quantizer` 仅在开启调色板复用时分配 64 KiB 最近色查询表。默认录制关闭复用，当前机器六个编码线程少分配 384 KiB。x64、x86 控制实验对比精确色和有损量化、复用开关、调色板重置路径，输出一致。
- 浸泡工具默认把全文件 WIC 校验放入短生命周期子进程，逐帧解码和合成，并核对尺寸、帧数和累计时长。子进程异常、超时或数据错误会使浸泡失败。截图、编辑与 PNG 往返、贴图和 GIF 录制仍在同一进程中循环。此变更隔离验收工具的解码容量波动，生产预览使用自己的 WIC 工作线程并单独验证。
- `-DiagnoseMemory` 保留同进程校验与 `VirtualQuery`、默认堆采样。正常门禁仍采用三轮暖机、空闲两秒，以及每轮私有提交、GDI、USER、句柄增长严格小于 5%。八小时判定同时核验 30 秒节奏。显示变更、会话锁定或断开会记录原因并结束测试。

私有提交使用 `PROCESS_MEMORY_COUNTERS_EX.PrivateUsage`。`VirtualQuery` 单独统计 `MEM_PRIVATE`，默认堆步行只用于诊断，其他保留区不会被归入默认堆在用字节。见微软文档 [PrivateUsage](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-process_memory_counters_ex)、[VirtualQuery](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-virtualquery)、[HeapWalk](https://learn.microsoft.com/en-us/windows/win32/api/heapapi/nf-heapapi-heapwalk)。

## 0.5.2 八小时试跑

实际启动 28,800 秒、30 秒一轮的测试，写出十分钟检查点。第 15 轮的私有提交在 Recorder 关闭后为 8,556,544 B，等待校验子进程退出后升到 9,273,344 B（相对基线 +9.58%），下一轮回落到 8,589,312 B。GDI 和 USER 全程稳定。资源门禁已失败，保留证据后于 675.219 秒停止本轮。见 [十分钟检查点](data/p6-0.5.2/eight-hour-checkpoint-10m.json)、[终止时报告](data/p6-0.5.2/eight-hour-trial-stopped.json) 和 [调用记录](data/p6-0.5.2/eight-hour-trial-invocation.json)。

独立控制把父进程 WIC PNG 工作与启动子进程拆开。未做 PNG 工作的父进程反复启动空子进程或真实 GIF 校验子进程，540 次采样的 `PrivateUsage` 均为 6,172,672 B。先做 PNG 编解码时，无子进程对照的同阶段增量为 0，空子进程出现 24,576–184,320 B 增量，真实校验子进程出现 24,576–335,872 B 增量。最大样本的默认堆在用量保持不变。PNG 仅编码的独立试验也复现短时提交增长。这些控制说明 PNG 工作及其后的进程启动路径都需要考虑。具体分配调用尚未由堆栈跟踪确定。

## 0.5.3 后续修正

- 将 GIF 校验子进程改为在暖机前启动，通过固定共享请求与事件逐轮复用。验证失败、取消、超时和父进程异常退出均有清理路径。混合对照中的 60 次重新启动校验进程增加了 28,672–176,128 B 父进程提交，60 次复用请求的父进程增量均为 0 B。该结果覆盖重复进程启动的影响，整体浸泡峰值仍需验证。见 [对照及复现方法](data/p6-0.5.3/process-worker-control.txt)。
- PNG 在编码器接受原生 BGRA 时直接写入扫描线，避免 `CreateBitmapFromMemory` 的整图副本与同格式转换器。Win11 x64 的八组 A/B 输出逐字节一致，覆盖透明度、奇数尺寸、内存 PNG 和剪贴板 PNG。两秒空闲的仅编码对照峰值增量由 664 KiB 降到 144 KiB，PNG 往返两次的绝对峰值相同，紧循环仍有波动。见 [仅编码原实现](data/p6-0.5.3/encode-20x2000.csv)、[仅编码新实现](data/p6-0.5.3/fast-encode-20x2000.csv) 和微软 [WritePixels 文档](https://learn.microsoft.com/en-us/windows/win32/api/wincodec/nf-wincodec-iwicbitmapframeencode-writepixels)。
- x64、x86 Debug 与 Release 四种配置编译通过。四种配置各通过 291 项单测、56,981 条断言。两项依赖真实屏幕的单测因 BitBlt 拒绝访问或句柄无效未通过，另跑剩余单测时显式排除这两项。两架构通过输出集成回归，各完成 200 次隔离窗口站的 PNG+DIB 剪贴板复制，像素、透明度及 GDI 检查均通过。两份构建 exe 的 Win7 静态导入检查与 Defender 定向扫描通过。见 [输出 x64](data/p6-0.5.3/output-x64.log)、[输出 x86](data/p6-0.5.3/output-x86.log) 和 [扫描](data/p6-0.5.3/defender.json)。
- 初次 0.5.3 集成浸泡在当前 RDP 会话的第一轮前报 `BitBlt: Access is denied`，完成 0 轮。此前运行过完整短测的 0.5.2 二进制，在同一桌面也以相同错误中止。见 [0.5.3 浸泡](data/p6-0.5.3/soak-desktop-blocked.json) 和 [0.5.2 同桌面对照](data/p6-0.5.3/soak-052-desktop-control.json)。
